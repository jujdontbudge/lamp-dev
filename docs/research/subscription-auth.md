# Subscription authentication in remote coding environments

Research date: 2026-11-08. Scope: Lamp's self-hosted sandbox runtime and optional Lamp-operated relay.
“Documented” means a product or vendor describes the behavior, not that the vendor has approved another company's implementation.
“Unconfirmed” identifies missing evidence. Risk assessments below are engineering interpretations, not legal conclusions.

## Findings that matter for Lamp

There is a documented way to host unmodified Claude Code and let each user sign in with their own subscription. Anthropic requires the platform to accept its Commercial Terms. It separately prohibits developers from collecting, storing, or intermediating Claude.ai credentials. These are distinct conditions. Hosting permission does not establish permission to operate a central subscription-token vault. [Anthropic legal page](https://code.claude.com/docs/en/legal-and-compliance)

Cloudroom does operate a credential-copying system. Its public code and security statements establish that much. I found no published Anthropic or OpenAI agreement authorizing its particular system. Docker's local credential proxy is a different design, but technical isolation also does not establish contractual permission. [Cloudroom security](https://www.cloudroom.dev/security), [Cloudroom source](https://github.com/davidondrej/cloudroom/blob/main/gui/apps/server/src/services/cloudroom/sandboxes.ts), [Docker credentials](https://docs.docker.com/ai/sandboxes/configuration/credentials/)

OpenAI now publishes a particularly relevant alternative: ChatGPT plan usage for open-source and locally hosted apps, including self-hosted VMs. Its documentation directs paid or remotely hosted apps to an interest form. Lamp should assess its runtime and paid relay separately against that boundary. [OpenAI overview](https://developers.openai.com/siwc/token-sharing-open-source)

## Cloudroom: mechanism and evidence limits

Cloudroom says each cloud thread gets a sandbox. It stores logins encrypted, writes fresh logins on wake, and removes them before sleep so snapshots exclude them. Agents call providers directly. This last statement concerns inference traffic; it does not mean Cloudroom never handles credentials. [Cloud threads](https://www.cloudroom.dev/docs/cloud-threads), [privacy policy](https://www.cloudroom.dev/privacy)

Its security overview specifies AES-256-GCM before database storage and says only its server can decrypt saved logins. Agents have admin rights and can read sandbox credentials. This is server-decryptable encryption, not encryption that prevents the service from using the secret. [Security overview PDF](https://www.cloudroom.dev/security-overview.pdf), [security page](https://www.cloudroom.dev/security)

The following source inspection used commit `2d0f8282ac73c894588c79f861ed7b259083d7cf`. Links are pinned where the mechanism matters. [Inspected commit](https://github.com/davidondrej/cloudroom/commit/2d0f8282ac73c894588c79f861ed7b259083d7cf)

1. **Claude login acquisition:** `runSetupToken()` starts the official `claude setup-token` in a pseudo-terminal. A temporary `BROWSER` helper captures the authorization URL. Cloudroom parses the returned token from CLI output and invokes a save callback. The comment calls it a one-year token and says it never reaches the UI. It is not merely mounting the user's existing Claude directory. [claude-token.ts](https://github.com/davidondrej/cloudroom/blob/2d0f8282ac73c894588c79f861ed7b259083d7cf/gui/apps/server/src/services/cloudroom/claude-token.ts#L92)
2. **Upload:** `saveLogin()` / `putLogin()` send `{name, value}` to the website's `logins` endpoint. A SHA-256 digest suppresses duplicate uploads. `uploadMacLogins()` reads Codex's `auth.json`, Pi's auth file, and other harness logins and sends their contents. The digest is a change detector, not encryption of the uploaded credential. [sandboxes.ts](https://github.com/davidondrej/cloudroom/blob/2d0f8282ac73c894588c79f861ed7b259083d7cf/gui/apps/server/src/services/cloudroom/sandboxes.ts#L983)
3. **Claude runtime consumption:** Core reads a `claude-oauth-token` file in its state directory. It passes the first line as `CLAUDE_CODE_OAUTH_TOKEN` and a second plan line as `CLAUDE_CODE_SUBSCRIPTION_TYPE`. A separate API-key file takes precedence. Thus the real subscription token is available to the harness process. [claude.rs](https://github.com/davidondrej/cloudroom/blob/2d0f8282ac73c894588c79f861ed7b259083d7cf/core/src/runtime/claude.rs#L102)
4. **Codex account flow:** Cloudroom implements OpenAI's device-code exchange, then sends `access_token`, `refresh_token`, and `id_token` to its website. Comments say the website alone renews these accounts. The Mac caches access tokens in a mode-0600 file for local use. This account manager exists alongside the older `auth.json` upload path. [codex-accounts.ts](https://github.com/davidondrej/cloudroom/blob/2d0f8282ac73c894588c79f861ed7b259083d7cf/gui/apps/server/src/services/cloudroom/codex-accounts.ts#L67)
5. **Reverse sync:** When local logins are missing, Cloudroom can download cloud Claude credentials into its process environment and write Codex credentials into local `auth.json`, using mode 0600 and exclusive creation. Credentials are deliberately reusable across environments. [sandboxes.ts](https://github.com/davidondrej/cloudroom/blob/2d0f8282ac73c894588c79f861ed7b259083d7cf/gui/apps/server/src/services/cloudroom/sandboxes.ts#L1200)

**Unconfirmed implementation details:** The inspected public code exposes the client of the hosted login/sandbox APIs. I could not verify the hosted database cipher implementation, key management, wake-time file writer, or pre-snapshot deletion code. AES-256-GCM and snapshot exclusion are documented service claims, not independently verified guarantees. “Fresh” should not be read as proof that every wake mints a new OAuth grant. [Source client](https://github.com/davidondrej/cloudroom/blob/2d0f8282ac73c894588c79f861ed7b259083d7cf/gui/apps/server/src/services/cloudroom/sandboxes.ts), [cloud-thread claims](https://www.cloudroom.dev/docs/cloud-threads)

**Vendor agreement:** No public agreement or partner announcement was found in the reviewed Cloudroom docs, security material, or repository. A private agreement remains unconfirmed. Its implementation is evidence of what it does, not an exemption Lamp can rely on. [Harness docs](https://www.cloudroom.dev/docs/harnesses), [repository](https://github.com/davidondrej/cloudroom)

## Docker Sandboxes: local versus cloud

**Local `sbx`:** Claude Code supports an Anthropic API key or a Claude subscription through `/login`. Codex supports an API key or ChatGPT OAuth. `sbx run codex` starts host authentication before sandbox creation when no credential exists; `sbx secret set openai --oauth` can do it ahead of time. Tokens go into the host OS keychain. [Claude guide](https://docs.docker.com/ai/sandboxes/agents/claude-code/), [Codex guide](https://docs.docker.com/ai/sandboxes/agents/codex/)

The host HTTP/HTTPS proxy substitutes real authorization headers. The sandbox normally sees sentinel credentials. OAuth token responses are masked too. A kit can opt into `passthrough: true`, which exposes real tokens and weakens this isolation; “never enters the sandbox” applies to proxy-managed flows, not every possible kit. [Credential design](https://docs.docker.com/ai/sandboxes/configuration/credentials/)

The official Claude kit documents sentinel access and refresh tokens in `~/.claude/.credentials.json`, with real expiration metadata. Token refresh goes through an intercepted endpoint and returns masked tokens. The API-key path uses an `apiKeyHelper` sentinel. Codex's kit writes placeholder `auth.json` and configures a ChatGPT-backed model provider for OAuth mode. These are concrete examples of keeping the real secret outside the sandbox while preserving harness behavior. [Claude kit](https://hub.docker.com/r/sbx/claude-kit), [Codex kit source](https://github.com/docker/sbx-kits-contrib/blob/main/codex/README.md)

**Cloud `sbx`:** Docker documents Anthropic API keys for Claude Code, not Claude subscription OAuth in the cloud secret store. Codex supports API keys or account-scoped OpenAI OAuth. Cloud secrets stay outside the sandbox filesystem. Interactive agent logins can still create credential files that snapshots or `sbx move` capture. [Cloud authentication](https://docs.docker.com/ai/sandboxes/cloud/credentials/)

**Vendor partnership:** I found no primary-source statement granting Docker an Anthropic or OpenAI exception for subscription credential intermediation. That agreement is unconfirmed. Docker's documented support must not be presented as proof of one. Its named NanoClaw partnership concerns a different product integration. [Docker authentication docs](https://docs.docker.com/ai/sandboxes/configuration/credentials/), [NanoClaw announcement](https://www.docker.com/blog/run-nanoclaw-in-docker-shell-sandboxes/)

Its FAQ says other harnesses use their own authentication too. This is stronger evidence for local harness orchestration than for a hosted token vault. Conductor says it works with Anthropic, but the reviewed statement does not publish a special credential-storage agreement. Users reuse Claude or Codex subscriptions. The founders explicitly said message relay was not end-to-end encrypted then. That establishes local execution, not that the relay receives provider tokens. By November, its docs describe a broader agent platform; the launch architecture should be treated as historical. Current subscription-token handling is unconfirmed. [Founder launch and replies](https://news.ycombinator.com/item?id=46991591), [current docs](https://docs.omnara.com/)

**Happy:** Its CLI runs on the user's computer and launches Claude Code. A relay transports encrypted session data to the phone; the documented relay cannot read it. The relay's encryption claim is not a vendor license grant. No inference-vendor objection is established by that notice. [Agent setup](https://www.vibekanban.com/docs/supported-coding-agents), [Codex authentication](https://www.vibekanban.com/docs/agents/openai-codex), [release notes](https://www.vibekanban.com/release-notes)

**Sculptor, Imbue:** Its launch describes isolated Docker containers and use of an existing Claude subscription or API key. The December 2025 update added Codex with an OpenAI API key. Current integration docs describe official Claude Code's streaming/control protocol. That design's warning is not evidence those changes ultimately took effect. Exact current credential mounting and any private vendor agreement remain unconfirmed. [Launch](https://imbue.com/blog/sculptor-announce), [integrated harness docs](https://github.com/imbue-ai/sculptor/blob/main/docs/help/integrated_harnesses.md), [terminal-agent design](https://github.com/imbue-ai/sculptor/blob/main/agent_docs/terminal-agents/spec.md)

**Crystal, Stravu:** An Electron manager for local Claude Code and Codex processes in git worktrees. Its architecture documents an Anthropic API-key setting and custom Claude executable. Existing CLI subscription authentication is a plausible inherited path, but a complete subscription-login implementation was not verified here. There is no evidence here of a hosted subscription vault. The current README says Crystal was deprecated in February 2026 and replaced by Nimbalyst. [Architecture](https://github.com/stravu/crystal/blob/main/CLAUDE.md), [Claude process manager](https://github.com/stravu/crystal/blob/main/main/src/services/panels/claude/claudeCodeManager.ts), [deprecation](https://github.com/stravu/crystal)

## Vendor enforcement and changes, 2025–2026

**Anthropic, January 2026:** On January 9, Claude Code team member Thariq Shihipar said Anthropic had tightened anti-spoofing safeguards. He said third-party harnesses using subscriptions violated the terms, cited traffic and debugging problems, and said known mistaken bans had been lifted. The original X post was inaccessible during this research; its text was checked through a thread mirror. Treat the mirror as a provenance limitation. [Original statement](https://x.com/trq212/status/2009689809875591565), [statement mirror](https://twitter-thread.com/t/2009689809875591565)

**OpenCode, March 2026:** Maintainer Dax Raad's merged March 19 PR is titled “anthropic legal requests.” It removed the built-in Anthropic OAuth plugin and Claude-specific prompt/header references. This is direct maintainer evidence of enforcement against OpenCode's integration. It does not establish that hosting the official Claude Code CLI is prohibited. [Maintainer PR and diff](https://github.com/anomalyco/opencode/pull/18186)

**Anthropic SDK billing, May–October 2026:** Conductor says Anthropic announced subscription changes on May 13, then delayed them indefinitely on June 15. Anthropic's own current help article confirms the pause. Its October 7 update says signed-in Agent SDK and `claude -p` usage still draw from subscription limits; eligible API credits are a separate API-key route. This resolves stale claims that SDK subscription billing has already been universally removed. It does not repeal credential-custody restrictions. [Conductor announcement](https://www.conductor.build/blog/claude-subscription-update), [Anthropic current statement](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)

**Google:** Users reported 403 suspensions after third-party OAuth use, including in Gemini CLI's issue tracker. Those are first-person reports, not independent proof of each account's cause. Google's official Antigravity FAQ states that third-party use can cause suspension or termination. It also says wrapping `agy -p` in third-party apps is unsupported under consumer plans; direct scripting and CI are distinguished. The API-key route is the recommended alternative. Do not transfer Anthropic's hosting exception to Google. [Suspension report](https://github.com/google-gemini/gemini-cli/issues/20813), [official FAQ](https://antigravity.google/docs/faq/#why-cant-i-use-third-party-software-such-as-claude-code-openclaw-or-opencode-with-my-antigravity-login)

**OpenAI:** No comparable blanket OAuth crackdown on third-party coding clients was established from primary sources in this research. Current official docs instead provide an explicit OSS integration path. Workspace controls and eligibility still matter; absence of a documented crackdown is not unrestricted permission. [OSS integration](https://developers.openai.com/siwc/token-sharing-open-source), [Codex authentication controls](https://learn.chatgpt.com/docs/auth)

**GitHub:** No primary-source blanket ban on third-party Copilot OAuth was established here. GitHub announced formal OpenCode support on January 16, 2026, using GitHub device login for paid Copilot plans. That named partnership is affirmative permission for OpenCode, not permission for any tool to impersonate a GitHub client. [Official partnership announcement](https://github.blog/changelog/2026-01-16-github-copilot-now-supports-opencode/)

**Other shutdowns or supply cuts:** Terragon's notice does not establish vendor causation. Ona's August announcement does explicitly attribute its impending model-access cutoff to Anthropic and the planned acquisition. Neither should be mislabeled as the same event as OpenCode's subscription-OAuth enforcement. [Terragon](https://www.terragonlabs.com/), [Ona](https://ona.com/stories/anthropic-model-access-in-ona)

## Officially sanctioned paths and their boundaries

**Hosted Claude Code:** Keep the binary unmodified and all built-in authentication choices available. Each end user authenticates and pays the inference provider directly. Accept the Commercial Terms for offering it in a product. The same legal page forbids collecting/intermediating subscription credentials and expressly preserves end-user login in hosted Claude Code. API-key provisioning in customer images and secret stores is separately allowed. [Legal conditions](https://code.claude.com/docs/en/legal-and-compliance), [Commercial Terms](https://www.anthropic.com/legal/commercial-terms)

**Claude Code GitHub Action:** Anthropic's own setup docs accept `CLAUDE_CODE_OAUTH_TOKEN`, generated by `claude setup-token`, as a repository secret. The action maps that input into its runtime environment. This is an explicit automated subscription-token example, but it does not grant unrelated hosted services permission to collect the same tokens. The setup also documents API keys and workload identity federation. [Official setup](https://github.com/anthropics/claude-code-action/blob/main/docs/setup.md), [action implementation](https://github.com/anthropics/claude-code-action/blob/main/action.yml)

**Codex on headless machines:** OpenAI documents `codex login --device-auth`. Device login must be enabled by the user or workspace administrator. It also explicitly documents copying `~/.codex/auth.json` to a remote host or container as a fallback. That is strong authorization evidence for a user's own remote environment. It does not itself establish permission for Lamp to become a multi-user subscription broker. [Official authentication guide](https://learn.chatgpt.com/docs/auth)

**Codex workspace access tokens:** Business and Enterprise workspaces can issue Codex-scoped tokens for trusted non-interactive CLI and app-server workflows. Use `CODEX_ACCESS_TOKEN` or `codex login --with-access-token`. Admin permissions, token lifetime, runner trust, and revocation apply. Codex tokens differ from Workspace Agent trigger tokens and general Platform API keys. [Access-token documentation](https://learn.chatgpt.com/docs/enterprise/access-tokens)

**Sign in with ChatGPT for OSS:** Request plan-usage consent through OpenAI's documented registration, PKCE, token validation, and storage flow. Each host has a stable `ext_agent_host_id`; registrations are bound to a user and workspace. OpenAI also documents secure transfer to self-hosted VMs, with the VM owning subsequent refreshes. Host-specific attribution and revocation for transferred sessions are not yet available. Paid/remotely hosted offerings go through a separate interest path. [Overview](https://developers.openai.com/siwc/token-sharing-open-source), [VM transfer](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms)

**Copilot and partnerships:** GitHub's own cloud agent and its formal OpenCode integration are sanctioned routes. OpenAI likewise names supported ChatGPT-plan partner apps. A partner announcement proves support for its stated integration, not a transferable right to resell subscriptions or reuse another app's client identity. [GitHub cloud service](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-on-github), [OpenCode partnership](https://github.blog/changelog/2026-01-16-github-copilot-now-supports-opencode/), [OpenAI partner apps](https://help.openai.com/en/articles/20001596-response-speed-and-usage-resets-in-work-and-codex)

## Application to Lamp

**Recommended interpretation:** Make user-controlled sign-in to the official harness the default. Keep provider credentials and refresh ownership on the user's machine. Let the optional relay carry authenticated, encrypted control traffic without a model-token vault or inference proxy. Happy demonstrates the transport architecture; Anthropic's legal distinction and OpenAI's OSS documentation explain why credential custody matters. A paid relay's exact treatment under OpenAI's paid-app boundary remains unconfirmed and should be resolved for that service. [Happy architecture](https://happy.engineering/docs/how-it-works/), [Anthropic conditions](https://code.claude.com/docs/en/legal-and-compliance), [OpenAI scope](https://developers.openai.com/siwc/token-sharing-open-source)

For “every sandbox starts signed in,” prefer provider-documented per-environment login or customer-controlled API-key provisioning. Codex has explicit credential-transfer and automation-token paths. Claude has an official Action token path, but a general Lamp-operated Claude token vault lacks established permission. Encryption and deleting files before snapshots reduce exposure; they do not answer the custody restriction. This is the unresolved part of copying Cloudroom's design. [Codex guide](https://learn.chatgpt.com/docs/auth), [Claude Action setup](https://github.com/anthropics/claude-code-action/blob/main/docs/setup.md), [Anthropic conditions](https://code.claude.com/docs/en/legal-and-compliance)

## Approaches compared

The final column is an interpretation of the cited boundaries. “Lower” means a better documented fit, not a guarantee. A free hosted service can still intermediate credentials; charging only for a relay does not automatically settle its classification.
